## 0. 这份文档要回答什么

Lecquy 的记忆与上下文这一年里被工具反复带偏、又反复收敛。散落在 `docs/` 各处的规范、执行指令、决策沉淀加起来十几份，单看任何一份都只是某个时间点的切片。这份文档把它们**压成一张当前理念地图**：

- 现在锁定的记忆设计理念是什么（不是历史上曾经的方案）
- 现在锁定的上下文 / system prompt 理念是什么
- compact（压缩）这条线现在长成什么样
- 这些定论分别是**从哪个旧方案、因为什么痛点**收敛过来的

读这份文档的目的：下次再有"要不要重做记忆 / 要不要改 prompt 结构"的念头时，先看这里——大多数方向已经踩过坑、已经有结论，不需要重走。

一句话总纲（贯穿全文）：

> **memory.db 是唯一权威长期记忆库；system 字段在会话内冻结不变；动态内容（记忆召回、日期、文件变更）一律下沉到 messages；压缩分三层、各管一段、永不重写真相源。**

## 1. 三条主线的当前定论（速览）

| 主线 | 旧路线（已弃） | 当前定论 | 收敛根因 |
|------|---------------|----------|----------|
| **记忆存储** | PostgreSQL + pgvector + pg_trgm | **SQLite + FTS5**，暂不引入向量检索 | 单机运维成本远高于收益；FTS5 的 BM25 已覆盖一期全部用例 |
| **记忆文件分层** | 计划把记忆拆成 `memory/facts.md` / `decisions.md` / `mistakes.md` 等分类 Markdown | **memory.db 承载分类（靠字段+标签）**，Markdown 只留 `MEMORY.md`（人工入口）+ `MEMORY.summary.md`（frozen snapshot） | Markdown 分类增加维护成本与污染风险，分类应由 DB 字段承担 |
| **记忆召回注入位** | 进 system prompt 第 6 层（StartupContext 之后的固定槽） | **挂当轮 API user message 内**，`<retrieved_memory priority="low">` 包裹 | 召回每轮都变，进 system 字段会每轮击穿 prompt cache |
| **system prompt 结构** | 7 层 36 子项 + `.lecquy/system-prompt/` 14~15 个模板 | **8 个常驻文件 + 会话级 FrozenSystemSnapshot**（BASE.md 一份大模板吃掉原 14 模板） | 动态片段混进 system 破坏缓存；26 子项对单人开发者认知过载 |
| **会话内变化生效** | 末位动态 `<env>` 块每轮重写进 system | **`<system_prompt_update>`**（cumulative since snapshot）注入 messages 尾部 | 让 system 字段会话内字节不变，最大化 prefix cache，同时"改完下一轮即生效" |
| **上下文压缩** | 单层事后 compact，按"50 条消息"触发 | **三层压缩**：in-loop（turn 内纯规则）+ 事件树投影 + 事后 compact（LLM 摘要，token-aware 触发） | 50 条阈值对工具型短对话不灵敏；单 turn 内工具输出可瞬间爆 window |
| **provider 适配** | 隐含按 Anthropic 能力假设 | **OpenAI-compatible 主路径**，Anthropic `cache_control` 只在 provider adapter 翻译 | 主路线是国产 / 本地模型（vLLM / Qwen / DeepSeek / GLM…），不能把可靠性押在 Anthropic 专属字段 |

下面分三节展开。每节都是"先讲当前定论，再用一小段讲它从哪儿来"。

## 2. 记忆设计理念（当前定论）

### 2.1 存储底座：SQLite + FTS5，一个文件就是全部

记忆的事实来源是 `.lecquy/memory/memory.db`，用 `better-sqlite3` + FTS5（内置全文检索，BM25 排序）。它是**唯一权威长期记忆库**，所有 Markdown 文件都只是它的摘要、入口或 fallback，不能反过来当主库。

约束：除非出现明确的语义相似度瓶颈（"忘了关键词但记得意思"那种召回），否则**不引入向量检索**。真要做时，优先 `sqlite-vec` 插件，其次才考虑换回 pgvector——核心是不为短期方便引入重型外部依赖。

> 背景：早期基线（`20260408-3`）选的是 PostgreSQL + pgvector + pg_trgm。实际开发发现单机场景下 PG 的依赖安装、迁移、连接管理运维成本远高于 SQLite，而一期根本没有向量检索需求。`20260508-9` 正式拍板换 SQLite，`db/` 下约 2000 行 PG 代码随之分阶段物理删除。这是"本地优先 / 删代码优先于加代码"原则的一次典型落地。

### 2.2 文件分层：每个文件回答一个不同的问题

记忆相关的常驻文件职责严格切开，不重叠：

| 文件 | 视角 | 描述对象 | 职责 |
|------|------|---------|------|
| `USER.md` | 第三方描述 | kira 本人 | 稳定画像 + 长期偏好（源文件软上限 4KB，不强制切片） |
| `SOUL.md` | 第二人称指令 | agent 自己 | 人格底色、沟通方式、对 kira 该是什么气质 |
| `IDENTITY.md` | 原则声明 | agent 的使命 | 使命、能力边界、默认行为原则 |
| `MEMORY.md` | 人工入口 | kira 和他的世界 | 人工可读的 memory 入口、维护说明、fallback；**不是主记忆库** |
| `MEMORY.summary.md` | 系统快照 | 长期稳定事实 | 可常驻的 frozen snapshot，由系统维护或人工整理 |
| `memory/memory.db` | 事实源 | 全部长期记忆 | 检索、标签、时间、重要性、置信度的权威来源 |

两个刻意保留的"双文件"拆分（即使按消融实验也不合并）：

- `SOUL.md` vs `IDENTITY.md`：人格 vs 使命的边界，长期审计价值大于合并省下的认知成本。
- `MEMORY.md` vs `MEMORY.summary.md`：人工入口 vs 系统维护 snapshot，职责完全不同。

> 背景：`20260512-2` 一度否决了 `memory/facts.md` / `decisions.md` / `mistakes.md` 这类按内容分类的 Markdown——记忆分类交给 DB 字段和标签，Markdown 分类只会增加维护成本和污染风险。这条结论沿用至今。`USER.md` / `SOUL.md` / `MEMORY.md` 由 kira 本人手写（`20260508-5`），因为"你是谁"只能本人写，丢给 codex 写是荒诞的。

### 2.3 记忆 schema：多维标签，写入时尽量打齐

`memory.db` 的记忆条目至少支持下列字段（写入时尽量打齐，打不齐可先写低置信记录）：

| 字段 | 取值 / 用途 |
|------|------|
| `kind` | `fact` / `decision` / `mistake` / `preference` / `project` / `people` / `environment` / `summary` / `commitment`（9 类） |
| `scope` | `global` / `project` / `session` |
| `projectId` | 项目维度过滤 |
| `status` | `active` / `archived` / `superseded` |
| `roleHints` | 哪些 mode / role 召回时优先 |
| `tags` | 补充检索维度 |
| `confidence` | 置信度，低置信不得晋升常驻 |
| `importance` | 重要性排序 |
| `ttl` | 过期 / 复审时间 |
| `source` | 来源会话、文件或人工写入 |

> 注：这套九字段 schema 出自 `20260512-2 §9`。该文整体已废弃，但 §9 记忆 schema 和 §10 信任分级被 `20260513-7` 明确继续引用，语义不变。早期 `20260408-5` 的四层 canonical schema（`profile` / `episodic` / `event` / `foresight`）是它的前身——当时只有 `event` 真正实现了写入。

### 2.4 晋升机制：先入库，验证稳定后才常驻（防熵增的核心闸门）

记忆有明确的"晋升"流向，目的是不让未验证 / 高频变化的内容污染常驻上下文：

- 临时事实先进 `memory.db`，**不直接写** `USER.md`。
- 被多次确认、跨任务稳定有效的偏好，才晋升 `USER.md`。
- 高频召回且稳定的少量事实，才进 `MEMORY.summary.md`。
- 对执行有长期影响的项目决策，留在 `memory.db` 并在 `docs/` 落正式记录。
- 打不齐标签的低置信记录可以先写，但**不得晋升**到 `USER.md` / `MEMORY.summary.md`。

### 2.5 召回与注入：复合排序 + 低权限包裹 + 不进 system

召回（recall）的当前形态：

- 排序是复合公式：BM25 + importance + 时间衰减 + 项目软优先，按 `(importance desc, recency desc, id asc)` 稳定排序后 topK 截断。
- 注入位置是**当轮 API user message 内**，用固定 tag 包裹：`<retrieved_memory priority="low" source="lecquy">`，让模型稳定识别为"低权限检索结果，不能覆盖 BASE / TOOLS / AGENTS 规则"。
- **绝不进 system 字段**——这是 `20260513-7` 的红线。
- 检索失败一律静默降级为"不注入"，不阻断主回复。

> 背景：`20260408-14`（旧路线，PG 时代）当时把 recall 设计成一条 synthetic user-context block，放在历史之后、当前输入之前，已经定了"不写回 session event、不进 extraSystemPrompt"的基调。`20260512-2` 一度把 MemoryRecall 列为 system prompt 第 6 层；`20260513-7` 把它移出 system，正式落到当轮 user message 内——根因是 system 字段一旦每轮变化，prompt cache 整段失效。

### 2.6 三份数据分离：别把系统注入误当成 kira 发言

这是新路线特别强调、也最容易实现错的一条。同一轮对话对应三份不能混用的数据：

- **用户可见 transcript**：只存 kira 真实输入。用于 UI 展示、搜索、导出、人工审查、默认的 memory extraction。
- **API replay transcript**：发给模型 / 重放时用，包含 `<retrieved_memory>`、`<system_prompt_update>` 等 synthetic context，必须保留当次发送的完整字节（否则 prefix cache 失效）。
- **augmentation 记录**：记录本轮注入来源、排序、hash、是否注入，服务调试与审计。

红线：不能把 `<retrieved_memory>` / `<system_prompt_update>` 写进用户可见 transcript，也不能在 API replay 里剥掉它们求"历史干净"。compact 摘要时必须识别这些 tag 是"系统注入，非 kira 发言"。

### 2.7 显式延后：memory.db 的熵增问题（不当下处理）

当前记忆系统**只写不删**，没有衰减 / 归档 / 矛盾合并。短期没事，但 JARVIS 化的 Lecquy 要用 3-5-10 年，第 18 个月这会变成灾难（DB 膨胀、过时记忆污染、矛盾决策并存）。

**为什么现在不做**：连"写"都还没做稳（flush 价值低、extraction 没真正跑起来），现在设计"删 / 衰减"是建在没成型的写策略上，必返工。

**启动触发条件**：memory 写入链路稳定 + 实际使用满 3-6 个月 + 出现第一次"过时记忆误导决策"的真实案例后，再单独立项。未来方向（占位）：时间衰减、置信/重要性打分、矛盾取代、冷热分层、用户可控的"遗忘/修正"接口。

## 3. 上下文 / system prompt 设计理念（当前定论）

### 3.1 FrozenSystemSnapshot：会话内 system 字段字节级冻结

核心契约：

1. 新会话创建时生成一份 `FrozenSystemSnapshot`，compact / resnapshot 后才重新生成。
2. 同一 snapshot 生命周期内，API `system` 字段**字节级不变**——不因日期、mode、模型、`USER.md` / `MEMORY.summary.md` 修改、skill 热更新而重写。
3. snapshot 内部按稳定来源固定顺序拼接（见下表），结尾放一个逻辑主断点。

FrozenSystemSnapshot 拼接顺序：

| 顺序 | 内容 | 来源 |
|------|------|------|
| 1 | Agent 基底（含 mode 子段） | `BASE.md` |
| 2 | 工具纪律 | `TOOLS.md` |
| 3 | 工具 inventory（schema 摘要） | 运行时生成，确定性序列化 |
| 4 | 项目约束 | `AGENTS.md` |
| 5 | 人格底色 | `SOUL.md` |
| 6 | 使命与边界 | `IDENTITY.md` |
| 7 | 稳定画像与偏好 | `USER.md` |
| 8 | 长期记忆 snapshot | `MEMORY.summary.md` |
| 9 | skills index | 运行时生成，字典序 |
| 10 | 命中的 SKILL.md（可选） | snapshot 生成时已激活的 skill |
| `<bp1>` | 逻辑主断点（仅 Anthropic adapter 翻译为 `cache_control`） | |

物理文件从旧路线的"10 常驻 + `system-prompt/` ≥14 模板"收敛到 **8 个常驻文件**：`BASE.md` / `TOOLS.md` / `AGENTS.md` / `SOUL.md` / `IDENTITY.md` / `USER.md` / `MEMORY.md` / `MEMORY.summary.md`（外加 `memory/memory.db` 和按需的 `skills/<name>/SKILL.md`）。原来散成 14 个模板的 system / mode / tooling / safety / runtime 全部合进 `BASE.md` 一份大模板。

> 背景：`20260512-2` 把 system prompt 拆成 7 层 36 子项、外加 `.lecquy/system-prompt/` 14~15 个模板。准备落代码时暴露两个问题——(1) `time.md` / capability block / preference 诊断 / MemoryRecall / LiveTurn 等动态片段混进 system 字段，prompt 前缀稳定性从"天级"掉到"单次启动级"；(2) 26 子项超过单人短期记忆容量，模块边界长期混乱。对标 Claude Code / Codex / opencode 三家生产实践（共同选择是"一份大模板 + 动态环境隔离 + 单 cache breakpoint"），`20260513-7` 收敛到现在这套，并进一步要求会话内 system 不变。

### 3.2 `<system_prompt_update>`：会话内变化的唯一出口（cumulative，不是 delta）

会话中途的可变内容**不改写 system**，而是在下一次用户问题前注入一个 `<system_prompt_update priority="high" source="lecquy">` 块。关键约定：

- **cumulative since snapshot**：每个 update 块表达的是"相对 snapshot 创建时点的当前累积变化"，不是"相对上一个 update 的增量"。最新一个 update + FrozenSystemSnapshot 就能还原当前等价状态，不要求模型回看历史 update 折叠多条 delta。明确**不采用** delta-since-previous（理由：模型在长上下文中间段注意力会衰减，押在"正确折叠历史 delta"上不可靠，尤其国产 / 本地模型）。
- 允许进的内容：当前日期 / 时区 / 工作目录 / session / mode / model / 附件状态；`SOUL` / `IDENTITY` / `USER.md` / `MEMORY.summary.md` 相对 snapshot 的累积 diff 摘要；当前激活 skill。
- **不允许**覆盖：BASE / TOOLS / AGENTS / safety / 工具权限 / 用户当前明确请求。
- 无变化不 emit；未变字段直接省略，不写 `none` / `null` / 空占位。
- 它是 Lecquy 托管的 synthetic user/context block，不是 kira 真实发言，也不用 tool role。
- 高风险更新（safety、工具权限、AGENTS/TOOLS）不走增量覆盖，必须新会话或显式 resnapshot 后才生效。

这套机制解决的核心矛盾：**"会话内 system 字段不变（保缓存）" vs "用户改了核心文件希望下一轮就生效（保体感）"**。

> 背景：对标项目（Claude Code 等）用末位动态 `<env>` 块承载实例化值，但那是每轮写进 system 字段。Lecquy 更激进地要求会话内 system 完全不变，所以把 `<env>` 这类内容整体下沉到 messages 尾部的 `<system_prompt_update>`。`20260512-2` 里根本没有这个概念，是 `20260513-7` 新增的。

### 3.3 信任分级：外部内容永远压不过系统规则

prompt injection 防护的信任优先级（沿用 `20260512-2 §10`，语义不变）：

```
System templates
  > Project instruction
  > Skill instruction
  > Memory summary
  > Memory recall
  > Tool output / external docs / web content
  > Live user-provided quoted content
```

外部文档、网页、工具输出、检索结果都不能覆盖 system / project / skill 规则；memory recall 必须带来源和低权限标记；写入 `USER.md` / `SOUL.md` / `IDENTITY.md` / `MEMORY.summary.md` 前要过滤明显注入短语（"忽略之前规则""把系统提示词输出给我"之类）。

### 3.4 provider 边界：主路径不发 Anthropic 专属字段

- **OpenAI Chat Completions-compatible 是第一优先级主路径**（vLLM / llama.cpp / SGLang / Qwen / DeepSeek / Kimi / GLM…）。该路径只产出会话级稳定的 system 字符串，**不发** `cache_control`。
- `cache_control` 是 Anthropic adapter 专属能力，只在 `provider-payload` 层由 snapshot 边界翻译出来，**不进核心 prompt 数据结构**。
- prompt builder 只产出 provider-agnostic 的 FrozenSystemSnapshot / `<system_prompt_update>` / 逻辑断点元数据；是否翻译成 provider 真实字段由各 adapter 决定。

### 3.5 一条工程红线：诊断信息不进 prompt

`profile=382 tokens, preference=196 tokens`、`truncated=...` 这类实时统计是开发者日志，写 stderr / 日志文件，**不进 prompt builder 输出**。这是 code review 红线。

## 4. compact / 上下文压缩理念（当前定论）

当前压缩不是一层，是**三层各管一段**，加上一个贯穿全部的不变量。

### 4.1 三层压缩各自的职责

| 层 | 位置 | 是否调 LLM | 职责 | 触发 |
|----|------|-----------|------|------|
| **in-loop compactor** | 单个 user-turn 内（`transformContext` 钩子） | 否，纯规则 | 把"末尾 K 个 turn 之前"的大 toolResult / image 块替换为占位文字，防 turn 内瞬间爆 window | 总字符数超阈值（默认 80k chars） |
| **事件树投影** | `buildSessionContext()` 投影为 LLM 视图 | 否 | 跨 turn 把 toolCall 块从 LLM 视图里砍掉（"工具失忆"） | 每次投影 |
| **事后 compact** | `executeRun` 结束后 / `memory/compact.ts` | 是，LLM 摘要 | 把历史轮次压成 summary + recent tail | token-aware（按 estimated token 超阈值，不再按 50 条消息） |

三个关键设计选择（写进代码注释，别回头"修复"）：

1. **跨 turn 的"工具失忆"是有意设计**，不是 bug。要让工具产出长期可用，应该走 `memory/` 抽取链路把它抽成长期记忆，而不是塞回 LLM raw 上下文。
2. **in-loop 压缩纯规则、零 LLM**。想做"in-loop LLM 摘要"是新课题，不是改这一层。
3. **事件树永远存原始数据**。截断只发生在 LLM 视图（投影 + `transformContext` 钩子），审计 / replay / 跨工具引用都靠原始事件树。compact 是派生层，不重写历史事件。

> 背景：旧路线（`20260408-16`）只有事后 compact 一层，按"50 条 message events"固定阈值触发，recent tail 保留 10 条。这对工具型短对话不灵敏——一轮里连读 5 个文件、单条工具输出上限 50k 字符，单 turn 最坏能累积 ~333k tokens，远超 128k window，但消息数可能还没到 50。`20260509-1` 因此补了 in-loop 压缩层，并把事后 compact 的触发从"消息数"改成"token-aware"（`20260430-15`）。

### 4.2 compact = snapshot 生命周期边界

新路线把 compact 和 system prompt 串起来了：

- **compact 是 FrozenSystemSnapshot 的生命周期边界**。compact 后旧 snapshot 的 hot cache 失效，下一轮懒创建一个 `createdReason: 'compact'` 的新 snapshot，把会话内累积的 `<system_prompt_update>` 吸收进去。
- restore 只接受当前 branch compact boundary 之后的 snapshot，branch sibling 不互相污染。
- **compact 同时是历史 memory / update bloat 的清理机会**：历史轮次的 `<retrieved_memory>` 块在摘要中可以丢弃（事实本就在 memory.db），`<system_prompt_update>` 可以吸收进新 snapshot——这不是额外成本，是顺带收益。
- compact 产出的用户可见摘要不得包含 `<retrieved_memory>` 原文；摘要 prompt 必须把这些 tag 识别为系统注入，不能写成"kira 说"。

### 4.3 上传层的两道体积闸（防爆的源头）

压缩之外，上传入口也设了上限，从源头堵住体积：入口 zod 校验（单图 5MB / 单文件 200k chars / 单条消息 8MB，超出直接拒绝），加内部静默截断兜底（真漏过来就替换为占位文字 / 截断，记 warn 不抛异常）。

## 5. 这些理念服务的最终目标

把上面三节收回到项目愿景：所有这些设计——SQLite 单文件、记忆分层与晋升、system 冻结、召回下沉、三层压缩、provider 边界——都只服务一个目标：

> **让单人 Agent 的长期执行力越用越懂 kira。**

具体到取舍标准，反复出现的几条判据：

- **本地优先**：核心上下文、长期记忆、项目规则都在本地可检查、可编辑、可迁移（SQLite 单文件、`.lecquy/` 明文文件）。
- **缓存命中是边际成本第一变量**：API 模式下 prompt cache 命中率比几乎所有其他工程指标都重要，这是 system 冻结 + 动态下沉的根本动机。
- **单人认知负荷是硬约束**：文件数要少、职责要硬。子项数量超过 7±2 就反成负担——这是从 26 子项收敛到 8 文件的根因。
- **删代码优先于加代码、半成品集成优于新模块**：PG → SQLite 删 2000 行、把写好没接的链路接上，都比写新东西收益高。
- **在愿景之外的"完整性 / 规整性 / 可扩展性"默认不做**。
