## 0. 背景、范围与已决事项

**为什么删**：CLAUDE.md 锁定记忆底座为 SQLite + FTS5，明确否决 PostgreSQL + pgvector，并记载"db/ 目录 PG 代码将物理删除"。本任务是**执行这一既定决定**，不是新决策。

**当前状态（已核实）**：`PG_ENABLED` 默认 `false`，所有 PG 路径都在它后面门控；会话持久化走文件 `.jsonl`；记忆召回默认走 SQLite。**没有任何当前在跑的功能依赖 PG**。

**已拍板范围（全删到底）**：
- PG 底座：`backend/src/db/`（client / 各 repository / migrate / migrations）。
- 各消费点的 PG 分支：`coordinator.ts`、`prompt-injector.ts`、`session-runtime-service.ts`、`server.ts`。
- 两个只跑在 PG 上的休眠功能：**RAG**（`rag/` + `db/knowledge-repository`）与 **foresight-sync**——**一并删除**。
- 已废弃的 flush 每日 dump 路径。
- PG 相关 env 变量与 dev PG 冒烟脚本。

**不在范围**（看到也别动）：`.lecquy/system-prompt/` 模板加载器（属功能迁移，CLAUDE.md §1.3 第 5 条，另案）；任何"风格不一致/抽象不优雅"的非 PG 代码（CLAUDE.md §2.1）。

## 1. 通用纪律

1. **开分支**：`git switch -c chore/remove-pg`。所有改动在分支上，便于整体回滚。
2. **先取基线绿**：动手前跑全量测试，记录通过状态；后续任何阶段红了都对照基线判因。
3. **按阶段顺序**：必须**先摘干净所有消费点的 PG 引用，最后再删 `db/`**——否则删了 `db/` 会留下一堆悬空 import。阶段顺序见 §2。
4. **每阶段一提交 + 测试 gate**：阶段内删完跑该阶段相关测试，绿了再进下一阶段。红了先修因，修不动就 revert 本阶段、上报。
5. **grep 先行 / grep 收尾**：每阶段开头按命令确认引用现状；结尾确认目标符号在 `backend/src` 已无残留。
6. **删测试随模块走**：删除一个模块时，其 `.test.ts` 一并删；不允许保留对已删模块的测试，也不允许改断言凑绿。
7. **靠 tsc 扫孤儿**：每阶段后 `npx tsc --noEmit`，清理因删除变孤儿的 import / 变量；不扩大到无关清理。
8. **遇到预期外的活引用就停手上报**，不要自行判断保留还是改写。

路径相对仓库根；后端在 `backend/`。测试命令以 `backend/package.json` 的 `scripts` 为准（大概率 vitest），下文 `npm test` 为占位。
